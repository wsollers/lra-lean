## The machinery this item builds on — already exists, don't rebuild it

**Correction (2026-08-27): an earlier draft of this prompt claimed ZFCSet
had no `HasPairing` instance and made "register one" step 1 of the Build
pass below. That was wrong — verified empirically (compiled a standalone
test, not just read the source) that it already exists, high priority,
for every axiomatic-set provider. There is nothing to register; go straight
to building `SetRelation`.**

- `LRA.Set.HasPairing` (`LRA/Set/Interface/Definitions/Pairing.lean`):
  `class HasPairing (Left Right : Type u) (Pair : outParam (Type u))`, with
  `OrderedPair := HasPairing.pair`.
- **Every axiomatic-set provider already has its own `priority := high`
  instance** (see DECISIONS.md R11 — this coordinator fixed the one gap,
  NBG, on 2026-08-27):

  | Provider | `HasPairing <Carrier> <Carrier> <Carrier>` backed by | Pairing injectivity |
  |---|---|---|
  | ZFCSet (`ZFCSet/Axioms/OrderedPair/Theorems.lean`) | `KuratowskiPair` | `KuratowskiPairInjective` — **`sorry`** |
  | TGSet (`TGSet/OrderedPair/Theorems.lean`) | `KuratowskiPair` (TGSet's own) | `PairingLaws` instance — **`sorry`** |
  | NBGSet (`NBGSet/Instances.lean`, fixed 2026-08-27) | `LRA.Set.Constructions.NBG.OrderedPair` (an `axiom`) | not separately stated |
  | Mathlib `ZFSet` (`Set/Constructions/Mathlib/ZFSet/Pairing.lean`) | `ZFSet.pair` | `ZFSet.pair_injective`/`pair_inj` — **already proven**, real Mathlib theorems, not `sorry` |

  Only the generic fallback (`instProdPairing : HasPairing Left Right
  (Left × Right) := ⟨Prod.mk⟩`, no explicit priority) uses `Prod` — and per
  R11, predicate-backed providers (`TypeSet`/`Alpha → Prop`, Mathlib's
  `Set Alpha`) *should* fall through to it: they have no same-carrier
  pairing object (elements and collections are different types by
  construction), so `Prod` on the element type is the structurally correct
  representation for them, not a gap.
- `LRA.Set.CartesianProductOf` (`LRA/Set/Interface/Definitions/CartesianProduct.lean`):
  `[HasPairing Left Right Pair] [Membership Left DomainObject]
  [Membership Right RangeObject] [HasSeparation Pair RelationObject]
  (left : DomainObject) (right : RangeObject) (ambientPairs : RelationObject)
  : RelationObject := HasSeparation.separation ambientPairs (fun member =>
  ∃ a b, member = OrderedPair a b ∧ a ∈ left ∧ b ∈ right)` — builds `A × B`
  as a genuine subset of an ambient collection of pairs, via `Separation`.
  **Already produces real object-language pairs for both ZFCSet and
  Mathlib's `ZFSet`** — no missing plumbing, confirmed by direct build.
- Both `ZFCSet` and Mathlib's `ZFSet` already have their own
  `HasSeparation` instance (`ZFCSet/Instances.lean`;
  `Mathlib/ZFSet/Instances.lean`).
- `LRA.Set.Interop.Providers.LRA.ZFC.ZFCSet` and
  `LRA.Set.Interop.Providers.Mathlib.ZF.ZFSet` — the named provider aliases
  to build against, per DECISIONS.md R2 (don't reference
  `LRA.Set.Constructions.ZFCSet` or bare `ZFSet` directly).

**Implication for the two constructions below**: since `CartesianProductOf`
already works correctly for *both* ZFCSet and Mathlib's `ZFSet`, and both
already have `HasSeparation`, the in-house and Mathlib impls can be built
the *same* way — the same generic `CartesianProductOf`/`HasSeparation`
skeleton, just instantiated at a different provider — rather than the
Mathlib side needing a structurally different `Set (Carrier × Carrier)`
approach. Consider whether that skeleton is worth writing once, generically,
and instantiating twice, versus two separately-named defs; either is fine,
record which you picked. Mathlib's `ZFSet` side also starts from a
strictly stronger position (pairing injectivity already proven, not
`sorry`'d) if that affects which one is easier to stand up first.

## Build pass — the actual new content

Nothing to register first (see correction above) — both constructions go
straight to building `SetRelation` on top of already-working machinery.

1. **`SetRelation` over ZFCSet** (`Relation/Constructions/Set/SetRelation.lean`):
   a relation on a `ZFCSet` carrier `A`, represented as a genuine subset of
   `A × A` built via `CartesianProductOf` + `HasSeparation`. Exact shape
   (adjust names/currying to taste, this is the shape not the final syntax):
   ```lean
   def SetRelation (A : LRA.Set.Interop.Providers.LRA.ZFC.ZFCSet) : Type :=
     {R : LRA.Set.Interop.Providers.LRA.ZFC.ZFCSet //
       R ⊆ CartesianProductOf A A <ambient collection of pairs>}
   ```
   Figure out what "ambient collection of pairs" should be for a first pass
   — `CartesianProductOf`'s `ambientPairs` parameter needs *some* enclosing
   set of pairs to separate out of; the natural choice is the powerset of
   `A × A`'s underlying pairs, i.e. build it from `A`'s own powerset via
   the existing `HasPowerset ZFCSet ZFCSet` instance, or from a
   `CollectionUnion`-style construction — check what ZFCSet's own existing
   axiom machinery makes easiest before inventing new plumbing. If this
   turns out awkward, a simpler first-pass definition
   (`SetRelation A := {R : ZFCSet // ∀ p ∈ R, ∃ a b, a ∈ A ∧ b ∈ A ∧ p =
   KuratowskiPair a b}`, sidestepping `CartesianProductOf` entirely) is an
   acceptable fallback — record which one you used and why in this file's
   outcome section.

2. **Bridge theorem** (data pairing with a real obligation, so `sorry` per
   DECISIONS.md R5): given `R : SetRelation A`, `fun x y => KuratowskiPair
   x y ∈ R.val` *is* an `Endorelation A` (or `Endorelation {x // x ∈ A}`,
   depending how the membership typing shakes out) — so anything downstream
   that still expects the old predicate-shaped relation has a way to get
   one out of a `SetRelation`. Name it something like
   `SetRelation.toEndorelation`.

3. **`Constructions/Mathlib/SetRelation.lean`**: the parallel construction
   over Mathlib's own `ZFSet` — *not* `Set (Carrier × Carrier)` (an earlier
   draft of this prompt recommended that; superseded now that `ZFSet`'s own
   `HasPairing`/`HasSeparation` are confirmed already wired up, making a
   genuinely parallel object-language construction free — see the machinery
   section above), and *not* `Rel` (Mathlib's `Rel α β := α → β → Prop` is
   the same predicate shape as `Endorelation`, not a second
   genuinely-different "relation is a set" representation, see README).
   Same shape as step 1, same bridge-theorem shape as step 2, `sorry`d.
   Since `ZFSet.pair_injective` is already proven (not `sorry`), this side
   may be the easier one to stand up first — consider building it before
   the ZFCSet side if that's true in practice, doesn't have to match the
   order listed here.

Every `theorem` in steps 2–3 gets `sorry`. The `SetRelation` type/def
itself (both providers) is *data* — not `Prop`-valued — so it gets written
for real, per DECISIONS.md R5.
