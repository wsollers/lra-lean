## The machinery this item builds on — already exists, don't rebuild it

- `LRA.Set.HasPairing` (`LRA/Set/Interface/Definitions/Pairing.lean`):
  `class HasPairing (Left Right : Type u) (Pair : outParam (Type u))`, with
  `OrderedPair := HasPairing.pair`. **Only one instance is currently
  registered**: `instProdPairing : HasPairing Left Right (Left × Right)` —
  Mathlib's `Prod`. There is **no** `HasPairing ZFCSet ZFCSet ZFCSet`
  instance yet.
- `LRA.Set.Constructions.ZFCSet.Axioms.KuratowskiPair`
  (`LRA/Set/Constructions/ZFCSet/Axioms/OrderedPair/Theorems.lean`):
  `noncomputable def KuratowskiPair (first second : Set) : Set` — this is
  the *genuine* ZFC-internal ordered pair (Kuratowski `{{a}, {a,b}}`), plus
  `KuratowskiPairInjective` and `SingletonMemberOfKuratowskiPair`. `Set`
  here is `ZFCSet`'s own local abbrev for itself.
- `LRA.Set.CartesianProductOf` (`LRA/Set/Interface/Definitions/CartesianProduct.lean`):
  `[HasPairing Left Right Pair] [Membership Left DomainObject]
  [Membership Right RangeObject] [HasSeparation Pair RelationObject]
  (left : DomainObject) (right : RangeObject) (ambientPairs : RelationObject)
  : RelationObject := HasSeparation.separation ambientPairs (fun member =>
  ∃ a b, member = OrderedPair a b ∧ a ∈ left ∧ b ∈ right)` — builds `A × B`
  as a genuine subset of an ambient collection of pairs, via `Separation`.
  Currently only usable with the `Prod` pairing (no ZFC instance registered).
- `ZFCSet` already has `HasSeparation ZFCSet ZFCSet` (`ZFCSet/Instances.lean`).
- `LRA.Set.Interop.Providers.LRA.ZFC.ZFCSet` — the named provider alias to
  build against (`LRA.Set.Interop.Providers.LRA.ZFC.ZFCSet := LRA.Set.
  Constructions.ZFCSet.Set`, per DECISIONS.md R2 — use this, don't reference
  `LRA.Set.Constructions.ZFCSet` directly).

**Implication**: `CartesianProductOf` currently gives you `Prod`-pairs, not
genuine ZFC pairs — using it as-is would be exactly the "ambient, not
object-language" shortcut README/DECISIONS say to avoid for this item. Step
1 below closes that gap.

## Build pass — the actual new content

1. **Register the ZFC pairing instance** (small, but load-bearing —
   everything else in this item depends on it existing):
   ```lean
   instance : LRA.Set.HasPairing
       LRA.Set.Interop.Providers.LRA.ZFC.ZFCSet
       LRA.Set.Interop.Providers.LRA.ZFC.ZFCSet
       LRA.Set.Interop.Providers.LRA.ZFC.ZFCSet :=
     ⟨LRA.Set.Constructions.ZFCSet.Axioms.KuratowskiPair⟩
   ```
   (Adjust the exact namespace path if `KuratowskiPair` isn't directly
   visible at that qualified name — check for an intermediate barrel.)
   Where this instance lives is a judgment call — `Relation/Constructions/
   Set/SetRelation.lean` itself is reasonable (it's the one place that
   needs it), rather than reaching into `LRA/Set/` to add it there (this
   item doesn't own that tree).

2. **`SetRelation`** (`Relation/Constructions/Set/SetRelation.lean`): a
   relation on a `ZFCSet` carrier `A`, represented as a genuine subset of
   `A × A` built via `CartesianProductOf` + `HasSeparation`, now that step 1
   makes `CartesianProductOf` produce real Kuratowski pairs for this carrier.
   Exact shape (adjust names/currying to taste, this is the shape not the
   final syntax):
   ```lean
   def SetRelation (A : LRA.Set.Interop.Providers.LRA.ZFC.ZFCSet) : Type :=
     {R : LRA.Set.Interop.Providers.LRA.ZFC.ZFCSet //
       R ⊆ CartesianProductOf A A <ambient collection of pairs>}
   ```
   Figure out what "ambient collection of pairs" should be for a first pass
   — `CartesianProductOf`'s `ambientPairs` parameter needs *some* enclosing
   set of pairs to separate out of; the natural choice is the powerset of
   `A × A`'s underlying pairs, i.e. build it from `A`'s own powerset via
   the existing `HasPowerset ZFCSet ZFCSet` instance, or from a
   `CollectionUnion`-style construction — check what ZFCSet's own existing
   axiom machinery makes easiest before inventing new plumbing. If this
   turns out awkward, a simpler first-pass definition
   (`SetRelation A := {R : ZFCSet // ∀ p ∈ R, ∃ a b, a ∈ A ∧ b ∈ A ∧ p =
   KuratowskiPair a b}`, sidestepping `CartesianProductOf` entirely) is an
   acceptable fallback — record which one you used and why in this file's
   outcome section.

3. **Bridge theorem** (data pairing with a real obligation, so `sorry` per
   DECISIONS.md R5): given `R : SetRelation A`, `fun x y => KuratowskiPair
   x y ∈ R.val` *is* an `Endorelation A` (or `Endorelation {x // x ∈ A}`,
   depending how the membership typing shakes out) — so anything downstream
   that still expects the old predicate-shaped relation has a way to get
   one out of a `SetRelation`. Name it something like
   `SetRelation.toEndorelation`.

4. **`Constructions/Mathlib/SetRelation.lean`**: the parallel construction
   using Mathlib's own `Set (Carrier × Carrier)` — *not* `Rel` (Mathlib's
   `Rel α β := α → β → Prop` is the same predicate shape as `Endorelation`,
   not a second genuinely-different "relation is a set" representation, see
   README). Same bridge-theorem shape as step 3, `sorry`d.

Everything in steps 3–4 that is a `theorem` gets `sorry`. Steps 1 (the
instance registration) and 2 (the `SetRelation` type/def itself) are *data*
— not `Prop`-valued — so they get written for real, per DECISIONS.md R5.
