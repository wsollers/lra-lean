**Correction #2 (2026-08-27): the Mathlib impl is `PredicateSet`, not
`ZFSet`.** An earlier draft of this section pointed the Mathlib
construction at Mathlib's `ZFSet` (reasoning that it has its own real
pairing/separation, making it "parallel" to the ZFCSet side). Superseded —
`ZFSet` is a fairly obscure corner of Mathlib this repo otherwise never
touches, and using it broke the naming convention every other subject in
this repo follows: `Constructions/Mathlib/*` means "the pragmatic bridge
using whatever Mathlib gives you for free" (see
`AlgebraicStructures/*/Constructions/Mathlib/Laws.lean`), and Mathlib's
everyday `Set` — already wired up in this repo as
`LRA.Set.Interop.Providers.Mathlib.Predicate.PredicateSet` — *is* that free
thing. It also gives a more illustrative contrast between the two impls
than two flavors of ZFC would: "relation as a first-class object of a
self-contained axiomatic universe" (ZFCSet) vs. "relation as an ordinary
typed predicate over pairs" (Mathlib).

This also makes the Mathlib construction dramatically simpler. Per the
"does a predicate-set need its own pair?" discussion in this coordinator's
originating conversation: no — `PredicateSet`'s elements and its
collections are different types by construction (unlike ZFC's
self-membership-closed universe), so there's no requirement that a
relation-on-`A` be encodable *as an element of `A`*. Plain `Prod` (`A × A`)
is the structurally correct representation, not a compromise, and it
already has full `PairingLaws` (injectivity) proven generically for *any*
two types via `instProdPairingLaws` — nothing provider-specific to build.
Concretely: `SetRelation (A : Type u) : Type u := LRA.Set.Interop.
Providers.Mathlib.Predicate.PredicateSet (A × A)` — no `CartesianProductOf`,
no `HasSeparation`, no `HasPairing` involved at all. See the Build pass
below.

## Build pass — the actual new content

Nothing to register first (see correction above) — both constructions go
straight to building `SetRelation` on top of already-working machinery.

1. **`SetRelation` over ZFCSet** (`Relation/Constructions/Set/SetRelation.lean`):
   a relation on a `ZFCSet` carrier `A`, represented as a genuine subset of
   `A × A` built via `CartesianProductOf` + `HasSeparation`. Exact shape
   (adjust names/currying to taste, this is the shape not the final syntax):
   ```lean
   def SetRelation (A : LRA.Set.Interop.Providers.LRA.ZFC.ZFCSet) : Type :=
     {R : LRA.Set.Interop.Providers.LRA.ZFC.ZFCSet //
       R ⊆ CartesianProductOf A A <ambient collection of pairs>}
   ```
   Figure out what "ambient collection of pairs" should be for a first pass
   — `CartesianProductOf`'s `ambientPairs` parameter needs *some* enclosing
   set of pairs to separate out of; the natural choice is the powerset of
   `A × A`'s underlying pairs, i.e. build it from `A`'s own powerset via
   the existing `HasPowerset ZFCSet ZFCSet` instance, or from a
   `CollectionUnion`-style construction — check what ZFCSet's own existing
   axiom machinery makes easiest before inventing new plumbing. If this
   turns out awkward, a simpler first-pass definition
   (`SetRelation A := {R : ZFCSet // ∀ p ∈ R, ∃ a b, a ∈ A ∧ b ∈ A ∧ p =
   KuratowskiPair a b}`, sidestepping `CartesianProductOf` entirely) is an
   acceptable fallback — record which one you used and why in this file's
   outcome section.

2. **Bridge theorem** (data pairing with a real obligation, so `sorry` per
   DECISIONS.md R5): given `R : SetRelation A`, `fun x y => KuratowskiPair
   x y ∈ R.val` *is* an `Endorelation A` (or `Endorelation {x // x ∈ A}`,
   depending how the membership typing shakes out) — so anything downstream
   that still expects the old predicate-shaped relation has a way to get
   one out of a `SetRelation`. Name it something like
   `SetRelation.toEndorelation`.

3. **`Constructions/Mathlib/SetRelation.lean`**: the `PredicateSet` impl —
   *not* `ZFSet`, superseded per Correction #2 above, and *not* `Rel`
   (Mathlib's `Rel α β := α → β → Prop` is the same predicate shape as
   `Endorelation`, not a second genuinely-different "relation is a set"
   representation, see README). Trivial by comparison to step 1:
   ```lean
   def SetRelation (A : Type u) : Type u :=
     LRA.Set.Interop.Providers.Mathlib.Predicate.PredicateSet (A × A)
   ```
   No ambient-pairs plumbing, no `HasPairing`/`HasSeparation` decisions to
   make — this is the whole construction.

4. **Bridge theorem, Mathlib side**: `SetRelation A = (A × A) → Prop` and
   `Endorelation A = A → A → Prop` are the same shape up to currying, so
   this bridge is close to definitional — likely `Function.curry`/`uncurry`
   or even `rfl`-adjacent, not the real work step 2's bridge is. **Still
   gets `sorry`, no exception for being trivial** — that's exactly the
   judgment call DECISIONS.md R5/D8 rules out; don't fill it in because it
   looks easy.

Every `theorem` in steps 2 and 4 gets `sorry`. The `SetRelation` type/def
itself (both providers) is *data* — not `Prop`-valued — so it gets written
for real, per DECISIONS.md R5.
