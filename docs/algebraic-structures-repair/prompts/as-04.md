# as-04 — AdditiveSemigroup

**STATUS: done, 2026-08-26.**

## What was found and fixed

Same `CarrierNonempty` gap as Magma (as-01) and Semigroup (as-02):
`AdditiveSemigroupLaws` only had `AddAssociative`, no nonemptiness field, despite
the user's own spec stating it directly ("`S` is a non-empty carrier set"). Fixed
by adding a nonemptiness field.

That fix surfaced a second, more serious problem, not seen in as-01–03: naming the
new field `CarrierNonempty` (matching `MultiplicativeSemigroupLaws`'s field name
exactly) broke `lake build` for every `class abbrev` in the tree that combines
*both* the additive and multiplicative semigroup sides — `SemiringLaws`,
`CommutativeSemiringWithoutZeroLaws`, `Ring/CommutativeRing/OrderedRing/
OrderedField Laws`. The error was misleading (`MulAssociative failed to
synthesize`, an entirely unrelated field) — root cause is that Lean's `class
abbrev` structure-extension mechanism merges identically-named fields from
independent parents, and that merge corrupts the auto-generated
parent-instance-derivation for the whole combined class. Fixed by renaming the
additive side's field to `AdditiveCarrierNonempty`, leaving
`MultiplicativeSemigroupLaws.CarrierNonempty` untouched (as-01/02/03 are already
`done`, and nothing combines Magma/Semigroup/CommutativeSemigroup with an
additive-side class). Recorded as a standing rule in `DECISIONS.md` D6: check for
field-name collisions against anything a later combining class might pull in
together, before naming a new field on an atomic `<X>Laws` class.

## Addendum, same day: superseded by D7

The `AdditiveCarrierNonempty` rename above was the first fix and it worked, but the
user then asked directly whether a `[Nonempty S]`-style constraint was an option
instead of a stored field. It is, and it's strictly better: a parameter of the same
type on two independent classes never collides (nothing is stored to merge), where a
stored field does the moment a `class abbrev` combines both. Given the choice between
keeping the rename (minimal, but leaves a landmine for the next field name that
happens to collide) or switching design tree-wide (bigger, but removes the whole
collision class permanently), the user chose to switch — see `DECISIONS.md` D7.

That meant revisiting `MagmaLaws`, `MultiplicativeSemigroupLaws`,
`CommutativeSemigroupLaws`, and `AdditiveSemigroupLaws` (as-01 through as-04, all
already `done`) to move nonemptiness from a stored field to `[Nonempty R]`/`[Nonempty
M]`, and mechanically propagating `[Nonempty R]` into the header of all 22 downstream
`class abbrev`/`abbrev` combining classes from tier 2 (`Monoid`) through tier 10
(`CompleteOrderedField`) that combine one of those four or extend something that
does — every subject in the tree except the lattice-family, `Archimedean`, and
`DiscreteInteger`. The 22-file mechanical sweep was delegated to a background agent
(pure "add `[Nonempty R]` to this header" edits, verified by direct read afterward);
the four foundational subjects' Constructions/Examples (which needed real
restructuring — `witness` term parameters became `[Nonempty ...]` instance-implicit
parameters, and every `CarrierNonempty := ...` line became a separate `instance :
Nonempty X := ...`) were done by hand.

Gates re-run after the full migration: `validate_structure.py` on `AdditiveSemigroup`
and the full `AlgebraicStructures` tree both pass. `lake build` on all four
foundational subjects + their Examples, the full `AlgebraicStructures` umbrella, and
`VolumeVICore`/`VolumeVIExamplesFailures` — 1918 jobs, clean. One file
(`CompleteOrderedField/Laws/Definition.lean`) didn't match the sweep agent's expected
docstring shape (its "Predicate logic" sections are unfolded-∀ propositions rather
than a literal signature copy) and was fixed by hand instead.

Still not committed (only commit when asked).
