# as-03 — CommutativeSemigroup

**STATUS: done, 2026-08-26.**

## What was found and fixed

Flagged in `DECISIONS.md` D6: `MultiplicativeCommutativeLaws` (this subject's only
`Laws` content) is atomic — commutativity alone, no associativity. Checked every
downstream user (`CommutativeMonoidLaws`, `CommutativeRingLaws`,
`CommutativeSemiringLaws`, `CommutativeSemiringWithoutZeroLaws`, `Field`,
`OrderedField`) — each of those already lists `MultiplicativeSemigroupLaws R`
*alongside* `MultiplicativeCommutativeLaws R` separately, so the atomic mixin being
commutativity-only is correct and deliberate, not a bug: folding associativity into
it would duplicate `MulAssociative` across six combining classes that already source
it elsewhere. Left `MultiplicativeCommutativeLaws` untouched.

The real gap: nothing in the tree names "commutative semigroup" as its own combining
law. Added `CommutativeSemigroupLaws` (`class abbrev ... := MultiplicativeSemigroupLaws
R, MultiplicativeCommutativeLaws R`) to `Interface/Laws/Definition.lean` — a `class
abbrev` over two already-existing LRA classes derives its instances automatically
from instances of the two parts, so this needed no new combinator proof, only the
declaration itself.

- `Constructions/Set/ClosedSubset.lean` — `ClosedSubsetCommutativeSemigroupLaws`:

  [Nonempty R]`.
