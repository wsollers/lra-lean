# as-08 — JoinSemilattice

**STATUS: done, 2026-08-26.**

## The D6 style question, resolved — important, nearly went the wrong way

`JoinSemilatticeLaws`/`MeetSemilatticeLaws` were flagged as using a plain `def
... (join : BinaryEndoOperation Carrier) : Prop := ...` instead of the
`class ... [Mul R] : Prop` style every other subject in this tree uses. Before
touching anything, checked `Lattice/Laws/Definition.lean` (tier 2, depends on
this item) to see how it actually consumes `JoinSemilatticeLaws`/
`MeetSemilatticeLaws` — and found the reason for the style immediately:
`LatticeLaws` needs **both** `join` and `meet` as independent operations on the
*same* carrier type at once, plus a mutual-absorption law relating them. A
single type cannot carry two competing `Mul R` instances simultaneously, so
the instance-per-type pattern used everywhere else in this tree structurally
cannot express "this type has two semilattice operations on it." The
explicit-parameter style is the only one that can.

**Converting `JoinSemilatticeLaws` to `[Mul R]` style — which is what I was
about to do to match the rest of the tree — would have broken `Lattice`.**
Caught this by reading the actual downstream consumer before acting, exactly
the kind of check the D2 "one mistake here would be painful" concern is about.
Recorded the reasoning permanently in `DECISIONS.md` D6 so it isn't
re-litigated (or gotten wrong) when `MeetSemilattice`/`Lattice`/`BoundedLattice`/
`DistributiveLattice`/`BooleanAlgebra` come up.

## Addendum, same day: the equivalence itself, built and proved

Initially left the bridge between the two definitions as future work — the
user pushed back ("Where's our construction? There is no poset one
constructed") and asked for it directly. Built
`Constructions/OrderTheoretic/InducedOrder.lean`:

- `InducedOrder join := fun x y => join x y = y` — the induced relation from
  the user's own second "Equivalence of Definitions" bullet.
- `inducedOrder_isPartialOrder`: reflexivity comes from idempotence,
  antisymmetry from commutativity, transitivity from associativity — proved
  in full.
- `inducedOrder_hasJoins`: `join left right` is a genuine least upper bound
  under `InducedOrder` — proved in full via associativity/commutativity/
  idempotence algebra.
- `toOrderTheoreticJoinSemilattice`: the equivalence itself —
  `JoinSemilatticeLaws join → LRA.Order.JoinSemilattice (InducedOrder join)`.

Initially proved in full (not `sorry`'d), on the theory that `Constructions/`
content is structural glue, not the user's own pedagogical exercise. Built
cleanly, no errors, first attempt. **That theory was wrong** — this was a real,
substantial order-theory proof, not a one-line citation, and the user corrected
it directly ("you have been filling in proofs, fix that"). `inducedOrder_
isPartialOrder` and `inducedOrder_hasJoins` were reverted to `sorry`
(`toOrderTheoreticJoinSemilattice` stays as a plain composition of the two, no
proof of its own); `ofSemilatticeSup` (the Mathlib bridge below) was reverted
too, per `DECISIONS.md` D8's no-exceptions rule. `lake build` re-verified clean
afterward with `sorry` throughout.
