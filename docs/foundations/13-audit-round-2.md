## 1. Corrections already applied

**`08-morphisms.md` §8.1–8.5 — the same mistake Round 1 caught, caught again.** This file presented group-specific vocabulary (normal subgroups, cosets, `ker(φ) = {e_S}`) as the formalization target. The repo's real `firstIsomorphismTheorem` (`LRA/UniversalAlgebra/KernelCongruence/Definition.lean`) is Signature/Model-generic, not group-specific, and carries 1 `sorry` plus ~20 supporting sorries — **not** "fully discharged" as the file previously claimed. Corrected throughout: every section now notes the real repo counterpart and its actual proof status. The mathematical content (ℝ²/ℤ² ≅ 𝕋² as groups) remains correct and is still the right target statement — what changed is the claim about how much of it is already checked in Lean.

**`05-order.md` §5.3 and `03-equivalences.md` §3.4 — closure-operator citation, corrected.** `03-equivalences.md` cited "Order interlude, Theorem 4.6" by number to justify the refinement-lattice join. No such theorem exists — not under that number in `05-order.md`, and not as any Lean declaration anywhere in `LRA/Order/` (confirmed absent despite Order being nine subdirectories deep otherwise: Bounds, Lattices, Density, Directedness, Morphisms, OrderedSets). This was a genuine three-way inconsistency: this exposition arc, the project's own memory notes, and the repo all treated the closure-operator theorem as settled, and none of them had actually built it. Both files corrected to state the mathematical argument is sound but currently rests on unbuilt machinery, not a citable theorem.

**`01-set.md` — undocumented backends added.** The file never described how Set is actually realized in Lean at all (this was previously only in project memory, inaccurately, as "three backends"). New §1.6 documents all six real backends, including two the project had no record of anywhere: `NBGSet` (von Neumann–Bernays–Gödel, thin, sorry-free) and `TypeSet` (predicate-based sets, `Alpha → Prop`, substantial — 1699-line `Operations.lean`, 73 sorries) — with a note that `TypeSet` is likely the most relevant backend for future Mathlib interop.

## 2. Confirmed genuine gaps (real work, not documentation drift)

- **Group-specific subgroup/kernel vocabulary is entirely unformalized.** No `Subgroup.lean`/`NormalSubgroup.lean` anywhere under `AlgebraicStructures/Group/`. The group case of everything in `08-morphisms.md` is a real, small, currently-unwritten corollary of the general Signature/Model machinery — not unbuilt mathematics, but genuinely absent Lean code.
- **`Sym(S)` is not a bundled `Group`.** The raw operations (`EndomapComposition`, `EndomapIdentity`) exist and are proved associative/unital, but nothing packages the bijective subset as a `Group` structure. Independently confirmed by the repo's own `OMNIBUS-GAP-LIST.md` (path-stale, content-valid: "packaging as algebraic structures remains").
- **The closure-operator abstraction itself** (Extensive + Monotone + Idempotent; fixed-points-form-a-complete-lattice) — small, well-scoped, currently load-bearing for a citation that points at nothing. Now the single highest-priority small addition per the audit's own ranking.

Order's is not — confirmed absent despite Order otherwise being the richest folder in the repo. The manifest's flag should be split going forward: Relation ✓, Order still open.
- **`MembershipSignature`** — a real, defined `Signature` (`LRA/Set/Interface/ModelTheory/LStructure.lean` and mirrored per-backend under `Set/Constructions/{ZFCSet,TGSet,GrothendieckUniverse,NBGSet}/`) — the single-binary-relation $\mathcal{L}_\in$ language matching `zfc-axioms-l-sentences.md` exactly, used throughout the model-theory layer. **`[REWORK — CORRECTED]`:** an earlier version of this row, sourced from `Set/ProofsToDo.md`, claimed this was planning-only. The remaining, still-open question is narrower than originally stated: whether `MembershipSignature` should be explicitly unified with the per-backend `Satisfy_Generic.lean` typeclass layer (`ExtensionalityLaw`, `MembershipLaws`, `SeparationLaws`, etc.), which currently exists alongside it rather than visibly building on it — a real design question, but not a missing-implementation question.
